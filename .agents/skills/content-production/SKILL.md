# 解説コンテンツの制作フロー

## 1. 制作前にユーザーへ入力を依頼する

台本・動画を作り始める前に、ユーザーの最新の指示、対象台本の`productionBrief`、この会話で回答済みの制作条件を確認する。既存条件がなければ、台本ノートの「制作ブリーフ」への入力をユーザーに依頼する。会話で直接回答してもらってもよい。

一度の依頼にまとめる項目：テーマ／参考URL、目標時間、想定視聴者、希望する構成、重点、扱わない内容、口調、その他の事前プロンプト、解説形式（1人／掛け合い／霊夢・魔理沙）、黒板図解の希望。構成確認を挟むかと、最終成果物（音声付き本編動画／台本のみ）も確認する。動画制作の依頼では本編MP4を最終成果物とし、途中の工程が終わっても元の動画化依頼を保持する。

ユーザーがまだ回答していない間は、制作条件に依存する構成・台本・動画を作り始めない。資料の所在確認など条件に依存しない準備は進めてよい。入力に期限を設けたり、時間経過を同意とみなしたりしない。

「お任せ」「指定なし」も有効な回答として扱い、採用する前提を短く明示して進める。すでに入力・承認済みなら再質問しない。編集済み台本の動画化は、その台本の制作条件と承認を引き継ぐ。条件が変わったときだけ不足分を尋ねる。

ブリーフの下書きは`editor/workspace/briefs/draft.json`、ユーザーが依頼文を作った時点のスナップショットは同フォルダー内のID別ディレクトリにある。他の題材の下書きを今回の条件として無断で流用しない。ユーザーが指定したスナップショットを優先する。

## 2. 資料確認と構成

台本の表記には[script-writing](../script-writing/SKILL.md)を使う。リポジトリが題材なら、ルートの`docs/REPOSITORY_LESSONS.md`に従い、コミットを固定して事実・資料の分析・教材独自の例を区別する。

目標時間には導入、まとめ、問いかけの待ち時間も含める。章ごとの狙い・要点・時間配分を作り、合計が目標に合うか確認する。指定内容を詰め込めない場合は、削る項目や分割案を示す。

`outlineFirst`がtrueなら、構成案を提示してユーザーの回答を待ち、承認・修正を反映してから台本へ進む。falseなら構成を整理したうえで指定された最終成果物まで進める。ユーザーがこの会話で明示した進め方を優先する。

## 3. 台本と尺

トップレベルの`targetMinutes`に目標分数、`productionBrief`に採用した制作条件を保存する。編集形式ではこれらは`meta`配下に入る。指定なしは0とし、架空の目標を作らない。

説明の量・構成で尺を調整する。極端な話速、長い無音、説明の途中での打ち切りで時間を合わせない。文字数からの推定は誤差を含む。既存の合成音声がそろっていれば、その長さと間から計算する。目標時間の指定だけで動画がその長さになるとは説明しない。

編集済み台本からの改訂では、ユーザーの文言・構成・メモを尊重し、元ファイルを残す。必要な増減と変更箇所を示す。台本ノートへ新しい編集用コピーとして読み込める形で渡す。

## 4. 演出と動画化

黒板は原則としてAIが台本から構成とアニメーションを設計する。ユーザーに項目の座標、表示順、秒数の入力を求めない。[黒板アニメーション](../../../docs/BOARD_ANIMATION.md)に沿い、何を理解させる動きかを場面ごとに決め、`boardAnimation`を生成する。単なるカードのフェードだけで済ませず、分類・圧縮・状態遷移・描画・比較など、説明対象そのものが分かる動きを選ぶ。既存の手動演出はユーザーの意図を尊重する。

ここでのAIはこの会話のアシスタント。ローカル画面にLLMが内蔵されていると説明しない。AIが作った設計を描画エンジンが再生する。ユーザーは場面プレビューと編集メモでフィードバックする。台本の変更後は対応する演出も再設計し、音声を変えた場合は新しい音声タイミングへ合わせる。模式図を実測グラフとして表示しない。

掛け合い・黒板図解では[対応形式](../../../docs/DIALOGUE_BOARD.md)を読み、話者IDと音声、場面の図、セリフごとの表示数・強調を保存する。図は字幕の丸写しではなく、比較・流れ・関係が分かる短い項目へ整理する。霊夢・魔理沙の画像とAquesTalkの音声は別条件であり、VOICEVOXによる代替音声をゆっくり音声と呼ばない。素材はローカルに置き、出典と利用条件を確認する。

セリフ単位の話速・追加の間・表情・ポーズを設定する。自動提案はルール方式であることを区別し、手動指定を保持する。必要に応じて画像・場面動画で確認する。

ユーザーが明示的に「台本のみ」と指定した依頼は台本JSONを成果物とする。単に構成・台本を先に作る工程へ分けただけで、元の動画制作依頼を取り消したとは扱わない。ユーザーの動画化依頼があれば、回答済みのブリーフを引き継ぎ、未保存の編集がないか確認して保存済みのスナップショットから生成する。過去の生成スクリプトで編集内容を上書きしない。

新規・改訂の2DアニメーションはRemotion＋React/SVGを標準方針とし、[黒板アニメーションの制作方式と品質確認](../../../docs/BOARD_ANIMATION.md#新しい制作方式と品質確認)に従う。まず理解目標と期待する変化を定義し、音声付きの代表場面を生成して、AI自身が重要フレームの画像と期待状態を照合・修正してから全編へ展開する。ライブラリの使用やデコード成功を、説明が伝わることの証明にしない。既存方式からの移行・導入状況は正確に記録する。

## 5. 検証と受け渡し

字幕の表示枠、場面・字幕の時刻、映像と音声の全編デコード、チャプター、素材クレジットを確認する。推定尺と完成尺を区別し、目標との大きな差があれば報告する。目視・試聴・実コード実行の確認範囲を正確に伝える。

動画・個人の作業データはGit管理外の保存先へ置く。再利用するコード・Skill・手順・検証記録はリポジトリの方針に従ってmainへ反映する。最終回答では成果物、完成尺、重要な未確認事項を簡潔に示す。

## 動画制作の完了条件

動画を依頼された場合、音声付き本編MP4が存在し、映像・音声の全編デコード、場面と字幕の時刻、完成尺、クレジットを検証してから完了とする。台本JSON、コード、静止画、無音プレビュー、生成ジョブの開始は本編の代わりにならない。`python verify_video.py <出力フォルダー>` が作る `delivery.json` を完了の証拠として保存する。最終回答の先頭で本編への再生リンクと完成尺を渡す。

依存ソフトや素材の不足は、既存の制作承認の範囲で公式配布・ローカル設定を確認して解消を試みる。解消できない障害が残る場合は「動画は未完成」と明示し、具体的な障害を伝える。途中の成果を動画制作の完了として報告しない。ユーザーが明示した台本のみ・構成確認の範囲は尊重する。
