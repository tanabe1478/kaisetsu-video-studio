# 解説コンテンツの制作フロー

## 1. 制作前にユーザーへ入力を依頼する

台本・動画を作り始める前に、ユーザーの最新の指示、対象台本の`productionBrief`、この会話で回答済みの制作条件を確認する。既存条件がなければ、台本ノートの「制作ブリーフ」への入力をユーザーに依頼する。会話で直接回答してもらってもよい。

一度の依頼にまとめる項目：テーマ／参考URL、目標時間、想定視聴者、希望する構成、重点、扱わない内容、口調、その他の事前プロンプト。「まず構成案を確認する」か「台本まで作る」かも確認する。

ユーザーがまだ回答していない間は、制作条件に依存する構成・台本・動画を作り始めない。資料の所在確認など条件に依存しない準備は進めてよい。入力に期限を設けたり、時間経過を同意とみなしたりしない。

「お任せ」「指定なし」も有効な回答として扱い、採用する前提を短く明示して進める。すでに入力・承認済みなら再質問しない。編集済み台本の動画化は、その台本の制作条件と承認を引き継ぐ。条件が変わったときだけ不足分を尋ねる。

ブリーフの下書きは`editor/workspace/briefs/draft.json`、ユーザーが依頼文を作った時点のスナップショットは同フォルダー内のID別ディレクトリにある。他の題材の下書きを今回の条件として無断で流用しない。ユーザーが指定したスナップショットを優先する。

## 2. 資料確認と構成

台本の表記には[script-writing](../script-writing/SKILL.md)を使う。リポジトリが題材なら、ルートの`docs/REPOSITORY_LESSONS.md`に従い、コミットを固定して事実・資料の分析・教材独自の例を区別する。

目標時間には導入、まとめ、問いかけの待ち時間も含める。章ごとの狙い・要点・時間配分を作り、合計が目標に合うか確認する。指定内容を詰め込めない場合は、削る項目や分割案を示す。

`outlineFirst`がtrueなら、構成案を提示してユーザーの回答を待ち、承認・修正を反映してから台本へ進む。falseなら構成を整理したうえで台本まで作る。ユーザーがこの会話で明示した進め方を優先する。

## 3. 台本と尺

トップレベルの`targetMinutes`に目標分数、`productionBrief`に採用した制作条件を保存する。編集形式ではこれらは`meta`配下に入る。指定なしは0とし、架空の目標を作らない。

説明の量・構成で尺を調整する。極端な話速、長い無音、説明の途中での打ち切りで時間を合わせない。文字数からの推定は誤差を含む。既存の合成音声がそろっていれば、その長さと間から計算する。目標時間の指定だけで動画がその長さになるとは説明しない。

編集済み台本からの改訂では、ユーザーの文言・構成・メモを尊重し、元ファイルを残す。必要な増減と変更箇所を示す。台本ノートへ新しい編集用コピーとして読み込める形で渡す。

## 4. 演出と動画化

セリフ単位の話速・追加の間・表情・ポーズを設定する。自動提案はルール方式であることを区別し、手動指定を保持する。必要に応じて画像・場面動画で確認する。

台本作成の依頼だけで全編動画を勝手に生成しない。ユーザーの動画化依頼があれば、回答済みのブリーフを引き継ぎ、未保存の編集がないか確認して保存済みのスナップショットから生成する。過去の生成スクリプトで編集内容を上書きしない。

## 5. 検証と受け渡し

字幕の表示枠、場面・字幕の時刻、映像と音声の全編デコード、チャプター、素材クレジットを確認する。推定尺と完成尺を区別し、目標との大きな差があれば報告する。目視・試聴・実コード実行の確認範囲を正確に伝える。

動画・個人の作業データはGit管理外の保存先へ置く。再利用するコード・Skill・手順・検証記録はリポジトリの方針に従ってmainへ反映する。最終回答では成果物、完成尺、重要な未確認事項を簡潔に示す。
